### B2. Bang-оператор на nullable — `ayahs_service.dart:184-186`

**Файл:** `lib/features/quran/data/ayahs_service.dart:184-186`

```dart
'UPDATE ayahs SET page = ?, juz = ?, hizb = ? '
'WHERE surah_id = ? AND ayah_number = ?',
[
  meta['page']!,      // ← bang на Map<String, int>?
  meta['juz']!,
  meta['hizb']!,
  ...
],
```

`meta` имеет тип `Map<String, int>`, но DTO `_fetchAndInsert` собирает его с fallback `?? 0` (см. `quran_com_api.dart:264-266`), поэтому `meta['page']` всегда `int`. Тем не менее тип `Map<String, int>` формально non-nullable по смыслу, но в `Map<String, int>?` поле может отсутствовать. Уточнить типобезопасность:

```dart
// Безопасный вариант:
final page = meta['page'];
if (page == null) continue;
...
```

Или в `quran_com_api.dart:263-267`:
```dart
result[key] = {
  if ((v['page_number'] as num?) != null) 'page': ...,
  ...
};
```

### B3. Утечка ValueNotifier-listener'ов — `providers.dart:393-405` и `428-439`

**Файл:** `lib/app/providers.dart:393-405`

```dart
final translationSyncStateProvider = StreamProvider<TranslationSyncState>((ref) {
  final service = ref.watch(quranTranslationSyncServiceProvider);
  final controller = StreamController<TranslationSyncState>();
  controller.add(service.state.value);
  void _onChange() {
    if (!controller.isClosed) controller.add(service.state.value);
  }
  service.state.addListener(_onChange);  // ← подписка без отписки
  ref.onDispose(controller.close);       // ← закрываем только StreamController
  return controller.stream;
});
```

`addListener` не имеет парного `removeListener` в `ref.onDispose`. На каждом invalidate provider'а накапливается мёртвый listener. Та же проблема в `ayahsSyncStateProvider` (строки 428-439).

**Исправление:**

```dart
final translationSyncStateProvider = StreamProvider<TranslationSyncState>((ref) {
  final service = ref.watch(quranTranslationSyncServiceProvider);
  final controller = StreamController<TranslationSyncState>();
  controller.add(service.state.value);
  void onChange() {
    if (!controller.isClosed) controller.add(service.state.value);
  }
  service.state.addListener(onChange);
  ref.onDispose(() {
    service.state.removeListener(onChange);  // ← добавлено
    controller.close();
  });
  return controller.stream;
});
```

### B4. `audio_cache_dao.dart:85-92` — `cast<String>()` после `where` + dead diagnostic code

**Файл:** `lib/core/database/daos/audio_cache_dao.dart:85-92`

```dart
return rows
    .map((r) => r.read<String>('reciter_id'))
    .where((s) => s != null)
    .cast<String>()
    .toSet();
```

`where` отфильтровывает null, но `cast<String>()` формально остаётся небезопасным. `read<String>` может вернуть `null` (Drift тип nullable). Использовать `whereType<String>()`:

```dart
return rows
    .map((r) => r.read<String>('reciter_id'))
    .whereType<String>()
    .toSet();
```

Дополнительно: `audio_cache_dao.dart:96-99` содержит диагностический комментарий "Сначала замерим TOTAL — если все запросы возвращают одинаковое число, значит WHERE игнорируется" — это dead code, который должен быть удалён после верификации.

### C1. Массовое использование `print()` вместо `developer.log()` / structured logger

**Файлы:**

**Пример — `audio_cache.dart:239`:**

```dart
// Стало:
```

### C2. N+1 UPDATE в цикле — `ayahs_service.dart:172-228`

**Файл:** `lib/features/quran/data/ayahs_service.dart:172-228`

```dart
for (final entry in metaMap.entries) {  // до 286 итераций (Аль-Бакара)
  ...
  await _db.customStatement(
    'UPDATE ayahs SET page = ?, juz = ?, hizb = ? '
    'WHERE surah_id = ? AND ayah_number = ?',
    [meta['page']!, meta['juz']!, meta['hizb']!, surahId, ayahNumber],
  );
}
```

Для Бакары (286 аятов) = 286 отдельных UPDATE → 286 транзакций. В Drift у `customStatement` это 286 round-trip'ов в нативный sqlite. На слабом устройстве — 1-3 секунды.

**Исправление — batch через `batch()`:**

```dart
await _db.batch((batch) {
  for (final entry in metaMap.entries) {
    final parts = entry.key.split(':');
    if (parts.length != 2) continue;
    final ayahNumber = int.tryParse(parts[1]);
    if (ayahNumber == null) continue;
    final meta = entry.value;
    batch.customStatement(
      'UPDATE ayahs SET page = ?, juz = ?, hizb = ? '
      'WHERE surah_id = ? AND ayah_number = ?',
      [meta['page'] ?? 0, meta['juz'] ?? 0, meta['hizb'] ?? 0, surahId, ayahNumber],
    );
  }
});
```

Это сократит время lazy fetch для большых сур в ~10-20x.

### C9. SharedPreferences не атомарны между ключами — `_writeManifest`

**Файл:** `lib/core/content/content_manifest.dart:268-278`

```dart

    'applied_at': DateTime.now().toUtc().toIso8601String(),
```

### C12. `DnsAwareAdapter` не кеширует DNS-резолвы — `dns_aware_dio.dart:50`

### C18. `ContentManifestRepository.apply` — `_snapshotPrevious` race

**Файл:** `lib/core/content/content_manifest.dart:251-266`

```dart
Future<void> apply(ContentManifest newManifest, ...) async {
  await _snapshotPrevious();  // ← snapshot
  await _writeManifest(newManifest, payloadSha256);  // ← write
}
```

Если между `_snapshotPrevious` и `_writeManifest` приложение упадёт, snapshot будет указывать на текущие (старые) данные, но новые данные уже подразумеваются. На следующем `rollback` восстановятся старые — норм. Но при `_writeManifest` мы пишем сначала version, потом hash, потом payload_sha256, потом applied_at — если упадёт между ними, snapshot не сделает write атомарным.

(см. C9 для исправления через JSON)

## 4. Рекомендации (Recommendations)

### R1. Внедрить структурированный logger

Заменить все `print` и `debugPrint` (≈20 мест) на `package:logging` или `dart:developer.log` с `name: 'XxxService'`. Текущий `developer.log` уже используется, но непоследовательно.

```dart
// lib/core/logging/app_logger.dart
class AppLogger {
  static void w(String tag, String message, {Object? error, StackTrace? stack}) {
    developer.log(message, name: tag, error: error, stackTrace: stack);
  }
}
```

### R2. Покрыть тестами критические сервисы

Из `pubspec.yaml:80-81` есть `sqflite_common_ffi` и `mocktail`, но тесты не добавлены. Критичные кандидаты:

- `ContentManifestRepository` — rollback-логика.
- `AudioCache._isLikelyValidMedia` — poison HTML detection.
- `AyahsService._fetchAndInsert` — UPDATE batching.
- `DnsAwareAdapter` — hostname resolution.

### R3. Изолировать fallback-логику в `getOrDownload` 

`audio_cache.dart` сейчас сам управляет fallback (primary → backup). Это нарушает SRP. Выделить `AudioSourceResolver` (есть упоминание в комментариях, но не реализован).

### R4. Унифицировать `quran_api` / `quran_com_api` / `mp3quran_api`

Три класса дублируют `Dio` конфигурацию (8s/12s timeouts, headers). Выделить `BaseQuranApiClient` или передавать `Dio` через DI.

### R5. Drift schema migrations → typed migration runner

`app_database.dart:393-395` имеет dead-code с комментарием про удалённый `_backfillTafsirRuNames`. Миграции должны быть в одном месте (`migrationRunner` callback), а не разбросаны по `if (currentVersion > X)`.

### R6. Кешировать `DnsResolver` результаты

См. C12. Каждый HTTP = 1 DoH-request. С кешем (TTL 5 min) — 1 DoH = 100+ HTTPs.

### R7. `ContentReadyNotifier` использует `AsyncNotifier` — но `bootstrap()` rethrows

```dart
Future<void> bootstrap() async {
  ...
  } catch (e, st) {
    state = AsyncValue.error(e, st);
    rethrow;  // ← перевыброс
  }
}
```

Перевыброс после установки `state = AsyncValue.error` — паттерн «установить и перебросить» — нормально, но семантика странная. Caller получает exception, но state уже error. Document or remove.

### R8. Использовать `package:riverpod_annotation` для типобезопасности

`pubspec.yaml:73-75` — `riverpod_generator: any` стоит, но используется минимально (один `@riverpod` proof-of-concept). Миграция всех 25+ провайдеров на `@riverpod` даст:
- Compile-time проверку возвращаемых типов.
- Auto-dispose возможности.
- Удаление boilerplate.

(Запланировано в Sprint 2.)
